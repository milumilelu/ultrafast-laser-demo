## 3. 结论与边界

- **正确性优先**：固定阈值 + 冻结几何 + 同相时，分组与逐脉冲参考的深度场最大绝对差为浮点舍入量级（实测 4.2e-22）；完整逐脉冲对照见 `tests/test_grouped_solver.py`（G08）。
- **加速来源**：分组把「逐脉冲的光束几何 + 窗口计算 + 状态提交」合并到块级；定点多脉冲因焦点相同可复用光束补丁（B01/B02/B03）。扫描工况（B04）焦点逐点变化，补丁不可复用，收益主要来自块级状态提交与计数合并。
- **不承诺固定加速倍数**：细则 12 节明确不得预先承诺「实时」「百万脉冲秒级」或任何固定倍数；本报告的数值只对**本机本环境**成立。
- **无收益即保留参考模式**：若某配置分组不比参考快，配置层不会强制启用；求解器记录实际 `n_blocks` / `n_rejected_blocks` 与局部误差估计，供外部核对。
- **未测项**：B03（100000 脉冲）的逐脉冲参考规模过大，未测其耗时；该项只报告分组模式的耗时与峰值内存。
- **内存口径**：峰值内存为 `tracemalloc` 统计的 Python 分配峰值，不包含部分 C 层分配（如 BLAS 工作区），也不是操作系统的 RSS。
- 公式核查 / 数值实现验证 / 实验复现三栏分开：本报告只做**数值实现验证与性能测量**，不含任何实验复现结论。

### 3.1 Numba 局部核：实测结论以数据为准，不默认启用

T16 要求「先测量局部计算开销，再决定是否引入 Numba」。实测对照（同配置只换后端）：

- B02 与 B02-numba 使用**完全相同的**网格、脉冲数与 batch_size，只替换局部核后端；实测加速比（`numba` 相对 `off`）为 **0.999×** → 判定：**无收益**（与 NumPy 基本持平或更慢）。
- 峰值内存：`off` **27.76 MB** vs `numba` **50.709 MB**（JIT 编译与 numba 运行时占用）；JIT 编译耗时 0.887 s，需与稳态开销分开看待（细则 12 节要求分别记录）。
- 原因：固定阈值对数核 `a = δ·ln(F/Fth)` 是**逐元素**运算，NumPy 的 `np.log` 已是 SIMD 向量化实现；Numba 版本（`njit`，**未并行**——不得并行依赖历史的事件轴） 需逐元素循环与调用调度开销，在 161²–512² 窗口下不占优。
- 因此本项目**默认后端保持 NumPy**（`solver.acceleration=off`）；`numba` 保留为可选后端，仅在实测有收益的规模上手动启用，且**缺失时自动回退并给出警告**。

### 3.2 长序列内存：不随事件数增长（B03 的核心目的）

- 事件数从 **10000** 增至 **100000**（×10.0），峰值内存仅从 27.76 MB 变为 29.312 MB（变化 1.55 MB，相对 5.6%）。
- 结论：事件**流式生成**、快照有限额，内存**不随已处理事件数增长**（符合细则 12 节「长序列检查内存是否随已处理事件不断增长」的要求）。
- 说明：分块处理只保留「当前块 + 块级累加器」，不构建全事件×全网格张量；块级累加器是**与网格同尺寸的单个数组**（不是事件维度张量），其占用由网格决定。

### 3.3 何时该用分组、何时该用参考

- **分组有收益**：焦点不动或变化很慢（定点多脉冲、小段扫描）——光束补丁可复用；以及事件数较大、块级状态提交摊薄了开销的场合。
- **分组无收益甚至更慢**：焦点逐点变化（大范围扫描）且事件数不多时，补丁不可复用、分块开销占比高。此时**保留参考模式**，不强制启用分组。
- 求解器始终记录 `n_blocks` / `n_rejected_blocks` / `n_beam_patches` / `patch_cache_hits` 与局部误差估计，供外部核对实际行为。
